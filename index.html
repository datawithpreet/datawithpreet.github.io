ABOUT

Hi, I’m Preet.

I solve the problems that sit between raw data and decisions that can’t be wrong: healthcare data fragmented across claims, clinical, enrollment, and operational systems; pipelines that teams quietly stop trusting; machine learning work that stalls because the data foundations were never built.

What’s distinctive about my approach is that governance, quality, and lineage get designed in from the start — not bolted on after something breaks. I’m problem-first and tool-agnostic: the same discipline applies whether the stack is Databricks or BigQuery, and the patterns that work in production become demos, architecture notes, and articles so others can learn from them.

Beyond the day job, I teach data engineering, judge hackathons, and mentor students — including through UMass Boston’s AI programs. I organize the Boston Databricks User Group, run a 1,500-member data engineering community, and write Healthcare for Data Engineers, a practical series for people working with healthcare data.

    01Healthcare Data Platform+
    01
    HEALTHCAREDATA PLATFORMPRODUCTION

    Healthcare Data Platform

    Problem
    A nephrology provider group’s revenue data lived across three EMRs — Athena, AdvancedMD, and Epic — with no unified model. Every analysis started from scratch.
    Context
    Revenue-cycle data on a legacy Azure stack (Data Factory, SSMS, SSIS). No lakehouse footprint — Databricks was stood up from networking to production.
    My contribution
    Built the entire RCM data model, unified the three EMRs into one business-logic-agnostic pipeline, and led the migration with a team of 6.
    Design decisions
    Chose Databricks + Snowflake over extending SSIS: a lakehouse for scale, a warehouse for analyst access — accepting the cost of retraining the team and refactoring the whole codebase.
    Results
    One pipeline for every EMR — any future EMR plugs in the same way. Delivered in 6 months.
    DatabricksDelta LakePySparkUnity Catalog

    02Model-Ready Data+
    02
    MLFEATURE ENGINEERINGPRODUCTION

    Model-Ready Data

    Problem
    A Medicaid program was losing ~$4M a year on wasted healthy-home visits — outreach reached the wrong members because no model identified who was likely to churn.
    Context
    Vendor claims files (Ciox, Datavant, Cotiviti — TXT, ZIP, CSV) ingested via Auto Loader into per-line-of-business tables: Medicare, Medicaid, Dual, D-SNP.
    My contribution
    Shipped the Medicaid member-churn ML model and the temporal feature pipelines behind it — point-in-time correct features with snapshot dates, lookback windows, and follow-up periods.
    Design decisions
    Built reusable feature definitions instead of one-off model tables — a slower first build, but every future model starts from the same governed features.
    Results
    Outcome: $4M in annual savings from a production Medicaid churn model.

    03Data Platform Modernization+
    03
    CLOUDMIGRATIONPRODUCTION

    Data Platform Modernization

    Problem
    Legacy ETL — SSIS packages and SSMS stored procedures — couldn’t keep up, and the organization had no lakehouse at all.
    Context
    An Azure shop moving to Databricks + Snowflake; Databricks stood up from scratch; deployments through Azure DevOps across multiple environments.
    My contribution
    Led the migration from Azure Data Factory / SSMS / SSIS to Databricks + Snowflake — refactored the whole codebase and stood up the platform.
    Design decisions
    Incremental cutover instead of a big-bang rewrite: both stacks ran during the transition — trading speed for safety on revenue-critical data.
    Results
    The full migration delivered in 6 months; the team now runs on the lakehouse.

    04HIPAA-Ready Data Pipeline+
    04
    HEALTHCAREGOVERNANCEOPEN SOURCE

    HIPAA-Ready Data Pipeline Framework

    Problem
    Healthcare data needs governance before it can be used — messy, incomplete records must be caught, explained, and quarantined, not silently passed through.
    Context
    Open-source framework built as a proper package, with deidentification, data quality, and audit. The demo uses synthetic data only — no client or employer data.
    My contribution
    Built the framework and its synthetic-data demo, including the governed / quarantined split and a reason for every quarantined record.
    Design decisions
    Quarantine with reasons instead of dropping bad records silently — every rejected record carries a reason, so the governed data stays trustworthy.
    Results
    Synthetic demo: 10,000 records in → 1,589 governed, 8,411 quarantined, in 0.143s. Quarantine reasons: missing field 3,557 / unparseable date 3,198 / invalid amount 1,646 / duplicate 10.

    Synthetic-data demo only — these numbers are from the demo, not a client system.
