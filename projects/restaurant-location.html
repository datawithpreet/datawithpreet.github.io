The Wrong Location Can Sink a Great Restaurant. Find the Right One With Data.

Opening a restaurant is one of the riskiest small-business bets there is — and location decides most of it. This agent evaluates candidate markets on demographics, demand, traffic, competitors, trade areas, and operating economics, then recommends where a restaurant has the strongest potential — before anyone signs a lease.

Real-world proof: Starbucks has used its Esri-based Atlas GIS platform for store planning — analyzing demographics, traffic, retail clusters, and transportation nodes. Chick-fil-A selected Esri's ArcGIS platform for site selection and market analytics, optimizing growth while minimizing competition impact and potential cannibalization.
Esri: Chick-fil-A case study ↗ · Starbucks' Atlas platform, summarized ↗

The business outcome

Today, a site decision runs on gut feel, broker anecdotes, and spreadsheets that never weigh the factors against each other. The outcome this project delivers: a ranked recommendation with explanations across candidate ZIP codes — every area scored on the same five factors, with a plain-English reason for the winner and a memory-guided re-run when the owner's goal changes (e.g., "avoid heavy competition").

A promising ZIP code can still be a poor investment if rent, competition, accessibility, delivery coverage, or supply-chain costs make the economics unattractive. The agent evaluates more than customer demand: it weighs the operating economics that decide whether a location survives year one.

How the agent works

One LocationAgent with a Planner and a Synthesizer, calling five evidence-gathering tools. The printed PLAN decomposes the goal into 13 steps — fetch per ZIP, analyze, score, synthesize — which you watch on screen.

1
Plan

Decomposes "where should I open a Chinese restaurant in Phoenix?" into per-ZIP evidence gathering, analysis, scoring, and synthesis steps.

2
fetch_area_data

Pulls each candidate ZIP's profile: businesses, ratings, review counts, and categories, plus area economics (produce-cost index, rent index, foot-traffic score).

3
analyze_review_quality

Reads review-quality signals for the cuisine in each area — are customers happy with the existing options, or is there an unmet bar to clear?

4
analyze_competitors

Maps competitor proximity and cuisine saturation: too many competitors too close is a red flag, but a cluster of strong Chinese restaurants can also prove the cuisine's draw (Hotelling logic).

5
estimate_economics

Weighs rent vs. expected demand — produce costs, rent index, and foot traffic turn a popular ZIP into an investable one, or rule it out.

6
score_location

Combines quality, economics, audience, Hotelling, and demand-gap into a transparent weighted score per ZIP. Turn 1 recommends 85012 (Uptown Phoenix).

7
Memory-guided re-plan

On the follow-up — "avoid heavy competition" — the agent finds the turn-1 scoring profile in memory, inverts the competitor rule (100 − 20·n), and re-ranks: 85003 (Downtown Phoenix), 1 competitor, foot-traffic 92, big demand gap. Same agent, different memory-guided plan, different answer.

Data engineering

The demo runs on ~60 synthetic businesses across 8 Phoenix-area ZIP codes in the Yelp schema (business_id, name, city, state, postal_code, lat/lon, stars, review_count, categories), with 24 synthetic reviews attached to Chinese competitors. Per-ZIP profiles (ZIP_PROFILES) carry produce-cost index, rent index, and foot-traffic scores. Scoring weights: quality 0.25, economics 0.20, audience 0.20, Hotelling 0.15, demand gap 0.20.

This is the classroom-friendly, fully offline, 60-seconds-to-run version of a real analysis — the companion repo ran the same class of analysis on the real Yelp dataset for Phoenix, AZ: Predicting the ideal location for a new restaurant using the Yelp dataset ↗.

Architecture

LayerWhat it does
PlannerDecomposes the goal into a 13-step investigation plan (fetch → analyze → score → synthesize).
Tool layerFive deterministic evidence tools: fetch_area_data, analyze_review_quality, analyze_competitors, estimate_economics, score_location.
SynthesizerRanks every candidate ZIP and writes the plain-English "why" for the recommendation.
MemorySeeded sessions (bubble-tea/Tempe, taco-truck/ASU) plus the turn-1 scoring profile; consulted on follow-up goals to re-plan.
Scoring modelTransparent weighted combination — no black box; every factor's contribution is printed.
Web UIapp.py serves the demo over stdlib http.server; no installs, no API keys, fully offline.

Implementation

  • Deterministic: stdlib only, no network, no API keys, no randomness — byte-identical output across runs; TEST-LOG.md records a 10/10 determinism gate.
  • Two turns: the ask ("where should I open a Chinese restaurant in Phoenix?"), then the follow-up ("avoid heavy competition") that reuses memory and inverts one rule.
  • Outputs: turn 1 recommends 85012 with Hotelling 100 (3 strong Chinese competitors proving the cuisine's draw); turn 2 recommends 85003 with the inverted-competitor explanation; full printed trace of PLAN, memory note, every tool call, and the synthesizer ranking.
  • Edge cases: TEST-LOG-EDGE.md covers adversarial inputs — the agent never crashes, never invents businesses, and says when data is insufficient.

Technical details

  • Run it: python3 app.py, then open http://localhost:8003 in Chrome and click Run live demo (binds 127.0.0.1, port 8003).
  • Repo: ynpreet/restaurant-location-agent ↗
