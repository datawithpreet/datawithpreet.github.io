Free Healthcare Data Projects

Three hands-on projects shared after my NYU Center for Data Science Capstone session. Each one takes you from messy, real-world-style data to something you could actually show an employer — with every step written out, A to Z.

Important — data safety: use synthetic or openly published demo data only for every project below. Never use real patient records, and never upload real health data to a public repo or notebook. If a dataset asks for credentials or a data-use agreement, pick the synthetic alternative listed instead.

What you need: Python, pandas, and a notebook (or Databricks Community Edition / Google Colab, if you prefer). No paid tools and no cloud account are required. Each project is designed to take roughly 3–6 hours.

Project 1Data modellingBeginner-friendly

1. Design a trustworthy EHR data model

Goal: turn messy, multi-source patient, encounter, lab and medication records into one clean, queryable data model that a clinician or analyst could actually trust.

Step by step

  1. Get synthetic data. Generate a small synthetic dataset (for example with Python's Faker, or the CMS Synthetic Public Use Files) with at least: patients, encounters, lab results and medications. Keep the row counts small — a few thousand rows is plenty.
  2. Profile it first. Before you model anything, write down: how many rows, how many missing values per column, duplicate patient IDs, impossible dates (discharge before admission), and conflicting units (mg vs mcg) in lab results.
  3. Draw the model. Sketch a simple star schema: a patient dimension, an encounter fact, and lab / medication facts linked by patient and encounter keys. Write one paragraph explaining every table and key — if you cannot explain it, it is not ready.
  4. Build it. Load the raw tables, apply your cleaning rules, and write the clean tables out (CSV, Parquet or a small database). Keep the raw and clean layers separate — never overwrite raw data.
  5. Prove it with checks. Add automated checks: no duplicate primary keys, no orphan encounters, lab values within plausible ranges, and a row-count reconciliation from raw to clean. Make the checks fail loudly, not silently.
  6. Answer three questions with it. For example: average length of stay by department, most common lab test per encounter type, and medication counts per patient. If a question is hard to answer, your model needs fixing — that is the lesson.

What breaks in real life (and what to watch for)

  • Two systems spelling the same patient differently — identity matching is a data problem, not a modelling afterthought.
  • Units and code systems changing over time — version your reference tables.
  • “Just one more column” from every team — governance is deciding what does not go in.

Stretch goal

Add a slowly-changing dimension for patient addresses, and a data-quality dashboard that reports your checks every time the pipeline runs.

Project 2Data engineeringIntermediate

2. From notebook to a production-ready pipeline

Goal: take a notebook that “works on my machine” and turn it into a pipeline that survives schema drift, late-arriving data, duplicates and re-runs — the exact story from the talk.

Step by step

  1. Start with the notebook. Write a notebook that reads a synthetic claims or encounters file, cleans it, and produces one summary table. Get it working end to end first.
  2. Extract the pipeline. Move the logic into functions or a script with three stages: bronze (raw, as landed), silver (cleaned, validated) and gold (aggregated, ready to query). Each stage writes its own output — never skip a stage.
  3. Break it on purpose. Feed it: a file with a renamed column, a file arriving two days late, a file with 5% duplicate rows, and an empty file. Write down what breaks each time.
  4. Fix each break. Add a schema check that rejects (and quarantines) bad files instead of crashing; add deduplication on a business key; make every stage idempotent, so re-running it produces the same result; log row counts at every stage.
  5. Schedule it. Run it on a schedule (even a simple cron job or a notebook job) for a week of synthetic daily files, and keep a run log: date, rows in, rows out, checks passed or failed.
  6. Write the runbook. One page: what the pipeline does, what each check means, and exactly what to do when a check fails. A pipeline without a runbook is not production-ready.

What breaks in real life (and what to watch for)

  • Silent schema changes from an upstream system — quarantine, don't guess.
  • Re-runs double-counting data — idempotency is non-negotiable.
  • Nobody knowing who owns a failure — name an owner for every stage.

Stretch goal

Add alerting (even a simple email or message on failure), partition the output by date, and backfill one historical month cleanly.

Project 3Machine learningGovernance

3. A governed healthcare ML project

Goal: build a simple risk-prediction model on synthetic data — and show the governance around it: validation, fairness checks and monitoring. The model is the easy part; the governance is the project.

Step by step

  1. Pick a synthetic problem. For example, predicting a 30-day return visit from synthetic encounter, diagnosis and lab features. Use a published synthetic dataset or generate one with a documented recipe — and write down its limitations.
  2. Split honestly. Split by time (train on earlier encounters, test on later ones), not randomly — random splits leak the future in healthcare data. Report this choice explicitly.
  3. Build a simple baseline first. A logistic regression or a small gradient-boosting model, with clear feature definitions. Beat the baseline before you add complexity.
  4. Validate beyond accuracy. Report precision, recall and calibration, not just accuracy. Check performance by subgroup (age band, sex, department) and write down any gap you find — do not hide it.
  5. Document the model. One model card: what it predicts, what data it was trained on, what it should never be used for, and its known limitations.
  6. Monitor it. Simulate a second month of data with a small distribution shift, re-score the model, and show how performance moves. Write the monitoring plan: what metric, what threshold, and what action follows a breach.

What breaks in real life (and what to watch for)

  • Training-serving skew: the data at prediction time is never as clean as training data.
  • Shortcut features that leak the answer — a discharge code that only exists after the outcome.
  • A model that works on average and fails for one group — subgroup checks are mandatory, not optional.

Stretch goal

Explain one prediction with SHAP or a similar method, and write the clinician-facing explanation in plain language — no jargon, no model internals.

How to show this work

Put each project in its own public repository with a README that states the goal, the data source (synthetic only), how to run it, and what the checks prove. Recruiters and capstone reviewers care far more about the checks, the runbook and the model card than about the model itself — that is the production-ready difference.
